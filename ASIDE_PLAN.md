## 0. What Aside is

A quiet personal assistant that lives in the background ("margin + Alfred": always there, never in the way, usable or ignorable). Python backend (FastAPI, Postgres + pgvector) plus a Chrome side-panel extension (`extension1/`). It captures tasks, schedule entries, notes and chat through one endpoint, records app/browser activity into sessions, writes a nightly review, compiles context for an LLM, and now talks to Gemini — but only for a call the user has read and approved.

**Two phases:** the pre-API phase is over. The project is now in the early post-API phase, but deliberately: one model, one recipe, user-approved calls only, no background LLM work yet.
**Core of the project (hardest, most important):** (1) context management, (2) long-term pattern recognition, (3) data quality.
**Resume goal:** the project must yield measured, honest claims (evals, ablations, cost/latency numbers), not keyword stuffing.
**Guiding rule: never get in the way.** No notifications/badges, no prompts, no auto-writes to the schedule, nothing that interrupts. Everything is visible in settings, undoable, quiet. (The chat approval card that used to be the one exception was removed on 2026-10-08: a chat message or "Draft tomorrow" now calls the model directly; the daily cap, the privacy layer and the trace are the guards.)

### 3.2 Context architecture (swappable parts)
- **Four concepts:** Source (returns Items) · Item (text, source, group, tokens, priority, provenance, confidence, valid dates, status) · Recipe (plain config file: which sources, order, budgets, simple filters; per situation) · Packer (greedy by priority within budgets). Nuance lives in item metadata and recipe filters, not code branches.
- **Priority order (user):** persistent file > skills > schedule > tasks > notes. Schedule outranks notes. Observations/history below, per recipe. Implemented as recipe-level source order; item-level priority only orders items *within* one source.
- **Formatting belongs to the renderer, not the source.** A source returns plain text plus an optional `group` label; `render()` owns all markdown. (v4 decision, after sources started emitting their own headings.)
- **Budgets are a fraction of the window AND an absolute ceiling** — `min(window × input_fraction, max_input_tokens)`. The fraction alone was written for a ~128k model and is meaningless against Gemini's 1M window. (v4 decision.)
- **Compile log:** one table, JSON blobs; each compile records offered / chosen / dropped / tokens; replayable under another recipe. **Context viewer** in settings ("why did it say that"). A compile is logged when it is *staged*, so compiles the user rejected are kept too.
- **Selector** (separate, removable): config value `off | rules | llm`. `off` = everything that fits the packer budgets. `rules` = situation tags. `llm` = small model that sees descriptors only, chooses only among optional items, falls back to rules. User distrusts small LLMs: off by default, compared against rules via replay. Embeddings are an optional strategy.
- **Usage tracking:** toggleable with no side effects; preferred mechanism = the reply returns ids of context pieces it used; fallback = local embedding overlap. Flags rarely-used sources in settings.
- **Result gate** (applies to every tool/DB/MCP result and to every context item): size caps, truncation with a pointer note, drop unused columns, read-only SQL with forced LIMIT, treat tool output as untrusted. **Per-source budget:** no source may exceed its slice.
- **Model agnostic:** thin `LLMClient` interface + model profile (window, cost, capabilities) in config; token estimate with safety margin; a fixed primary model for extraction/generation/evals; always log the model per call. Model costs are a review-dated fact, not a constant.
- **Persistent file always-on core:** identity & stable facts, hard preferences & constraints, weekday/weekend routine skeleton. Chosen per situation: goals/current focus, people, observations.
- **Cap per call:** at most 3 observations injected; at most 2 skills loaded (~600 tokens each).

### 3.3 Memory rules
- Conflicting new fact: keep old and new together, new tagged provisional; old is retired once the new one has been seen on 3 separate days with no contradiction (old stays in the log, hidden from context).
- Note beats persistent file in context, but is provisional until repeated. Conflicts settled quietly; the user fixes things in settings.
- Writers: the user, and the agent when fairly confident (any section including static); every write is logged and undoable.
- Promotion on repeats, patterns, and the user's say-so.
- Entry fields: text, source (user/agent/note/pattern), created, last confirmed, evidence count, status. Nothing else.
- "Mark wrong" = log it, nothing else. Hidden gesture: `wrong:` prefix; long-press on a reply as backup; also a hidden gesture on a row of the What changed page. Each mark stores the compile-log id of the **sent** call so it becomes a replayable regression case. No visible thumbs.
- Raw conversations are low value; keep what is affordable. Edits/deletes of past data are logged; pruning later; past schedule entries kept ~3 months.
- Persistent-file size cap depends on model and resources; evict least-evidence / longest-unused; tuned by experiment.

### 3.4 Skills
A skill is a specific format, a set of steps/instructions, or a decision tree. If it fits in one sentence it belongs in the persistent file. Descriptor-first (name, "use this when", what it affects); full body loaded on demand by rules (tag match, word-boundary). Cap 2 per call, ~600 tokens each (warn at save). Usage count and correction count per skill, shown in settings; never-used and often-corrected skills flagged. The user edits skills by hand; the agent never edits skills.

### 3.5 Statements, extraction, patterns
- **Statements:** `journal:` entries (journal notes), plain notes, and schedule-mode instructions. Raw text immutable.
- **Extractor (needs §3.9's privacy layer first):** produces **candidate items** {type: actual|plan|prediction|constraint|preference, text, effect, valid-for dates, confidence, source id, reason}. Journal weighs more than a plain note. Doubtful items are shelved (kept, unused). Items expire with their dates. Viewable/deletable in settings with reasons. Re-runnable with a better model. **One batched call per night over the day's statements — never one call per note.**
- **Instructions:** schedule-mode text is stored as a one-shot instruction scoped to a date range (default tomorrow) and kept afterwards for the pattern finder.
- **Review shows nothing from the journal.** Past-day journal entries are ignored in v1. Review corrections happen in settings, not by telling it.
- **Patterns:** observations only, never facts. Lifecycle: candidate → active (3 occurrences) → shown as "hike?" after 2 consecutive misses → dropped at 3 misses. Code detects (statistics); the LLM only names/explains later, at most once a day. Interests: weekday vs weekend routines; planned vs actual duration; focus hours; low "intentional activity" days; slipping tasks. **Intentional** = time overlapping a schedule entry or related to a task; the rest is "unplanned", never "bad". **Slip** = due date moved later repeatedly, expired, or pending past due. Inputs: tasks, sessions, schedules (not raw notes) plus extracted day facts. Pass runs at **1 PM and 9 PM**; if the laptop is off, no predictions that cycle. Observations viewable and deletable in settings. Recurrence algorithms (e.g. "first Sunday") are parked until real data exists. Title grouping pre-API: shared words only; synonyms need LLM/tag.
- **Provenance:** entries default to `user`; only accepted generator output is `generated`; a manual edit of a generated entry sets `edited_by_user`; Google-side changes count as user. Patterns count user + edited. The instruction text behind a draft is stored.

### 3.6 Schedule generation
On request only, **tomorrow only**; buttons in the panel and on the review page; if the user built any part of tomorrow the button stays off entirely. Flow: (1) code gathers: user entries for tomorrow, tasks due, last same-weekday snapshot, top-3 observations, instructions covering tomorrow, candidate items valid for tomorrow, persistent-file constraints, free-slot map; (2) LLM drafts meaningful blocks and **time-blocks the tasks that should be done that day** (cloud plan, 2026-10-08: it picks the duration from context; a block carries `task_id`, saved on the schedule row; overdue and postponed tasks are offered, stale ones are dropped first; no meal/sleep filler) with stored reasons — as a user-initiated call, so it goes through the approval card; (3) code validates (overlaps, waking hours, 30-min default, IST); (4) editable draft shown in the **panel without reasons**; accept per entry or all; accepted entries are tagged `generated`; (5) reasons visible in settings; (6) a follow-up instruction regenerates with untouched entries locked; (7) log inputs/draft/final. **Only two schedules matter for learning, review and patterns: the first generated draft and the final one (the last state of the day). Edits in between stay in `schedule_log` for audit/undo only (user decision 2026-10-07) and must not feed review, patterns or draft-vs-final.** **Chat never auto-writes**; the small LLM is not a write router; Ctrl+Enter is where a classifier may help later. A rule-based placeholder generator (copy last same weekday, fill free slots) is the fallback and the baseline to measure against.

### 3.7 Evals
Constraint-adherence: seed a constraint at turn 1, check turns 5/10/15/20, with and without pinning. Cross-session: state a preference in session 1, check it is applied unprompted in session 2. Constraints must be checkable by code (e.g. "under 50 words", "no emojis"). Plus a standard question set (10–20) and "feel" (feel takes priority). Replay of `wrong:`-marked cases. Ratings passive; value is as saved test cases. **Free-tier re-scope:** the full matrix is 40+ calls per scenario. Develop entirely against `FakeClient`, then spend real calls on 2–3 scenarios.

### 3.8 Data quality (collect early; this is the asset)
Schedule edit log + origin flag + nightly snapshot; task due-change log (slip signal); monitoring pause log + collector heartbeat (gap reasons); nightly **day record** (schedule snapshot, session stats, completed tasks, extracted day facts) that patterns read; retention config; data-gaps view in settings (month heatmap, gap list with reasons, collector/ingestor health, "beautifully"). User statements about their day are the planned-vs-actual signal along with the user's edits. **The synthetic seed (M5) writes into these same tables with recent dates, so it must be torn down before any of this is read as real.**

### 3.9 LLM access policy (NEW in v4)
- **Two tiers.** *User-initiated* (chat, schedule generation): the call is compiled and sent when the user asks (the approval card was removed 2026-10-08 by the user's decision; the daily cap and the privacy layer remain the controls). *Background* (extraction, pattern naming, nightly jobs): never prompts, runs only inside the quota, logged after the fact and auditable in settings — and stays **off** until the privacy layer exists.
- **One chokepoint.** Every call goes through `ApprovedClient` (`llm/approved.py`), returned by `llm/factory.create_client`. A route that constructs a raw adapter is a bug. This is structural, not a convention, because the gate is the only thing standing between a background job and the free-tier allowance.
- **Quota, not cost.** `daily_call_cap` in `config.toml` `[llm]`, counted as today's (IST) `llm_trace` rows. No new table: the user decided approvals and rejections need not be persisted. Failed calls must record a trace too, because a failure still consumes allowance.
- **Free-tier data use.** Free-tier prompts may be used to improve the provider's products. The approval card protects the user today only because they read it; that protection disappears the moment a background job sends anything. So: a per-source allow/deny privacy layer (starting with `journal`-tagged notes excluded) lands in M9 and is a hard prerequisite for `background_enabled = true`.
- **Model facts expire.** Gemini list prices rise on 2027-01-01. `config/models.toml` carries the figures with a note saying where they came from and when to re-check.
- **Call-path rules, from measurement (2026-10-07, `docs/gemini_api_findings.md`).** (1) Never call a Gemini 3.x model at its default thinking: set `reasoning_effort` in the profile. (2) Leave room for thinking in `max_tokens` and treat `finish_reason == "length"` as an incomplete reply, never as a normal one. (3) Latency is load-driven, so each attempt has a short timeout (45 s) and a different model is tried once on 503/timeout/429; never retry the same overloaded model, and never retry a 400/401. (4) Every attempt, including the failed and the fallback ones, is gated and traced, because failures use allowance. (5) The daily count follows the provider's day (midnight Pacific), not IST. (6) The remaining quota cannot be read from the API, so the local counter is the only instrument.
- **The review stays code-only.** `review/generate.py` is a pure builder and must remain one; a nightly job that silently calls the API is exactly the interruption §0 forbids.
